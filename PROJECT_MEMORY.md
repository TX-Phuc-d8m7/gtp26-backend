## 0. Current Implementation Snapshot - 2026-05-18

This section supersedes older notes below when they conflict.

### Major problems solved

1. **`soft_tags` was overloaded.**
   - Problem: taste, meal time, occasion, method, nutrition, cuisine, and medical signals were mixed in one array.
   - Solution used: relabeled/cleaned food data now separates:
     - `soft_tags`
     - `taste_profile`
     - `meal_context`
     - `occasion_context`
   - Runtime DB, seed, response schema, embedding text, and search scoring now use these fields.

2. **Keyword ingredient filtering was too brittle.**
   - Problem: raw substring matching could miss variants such as `bắp bò`, `gân bò`, `bò mỹ`, or falsely match ambiguous words.
   - Solution used: add `core_ingredient_keys` to foods, generated from reviewed alias rules:
     - `base:*`: normalized ingredient key.
     - `canon:*`: canonical ingredient, for example `canon:thit_bo`.
     - `group:*`: broader group, for example `group:thit_bo`, `group:hai_san`.
   - Medical/user ingredient filters now use `Food.core_ingredient_keys` with PostgreSQL array overlap instead of loose `ILIKE` over ingredient strings.

3. **Alias rules needed admin extensibility without redeploy.**
   - Problem: new aliases such as `thịt bò Úc` would require code changes.
   - Solution used: hybrid alias override:
     - Baseline reviewed alias rules stay in code/data.
     - Admin override table `ingredient_alias_overrides` adds extra aliases from DB.
     - API prefix: `/admin/ingredient-alias-overrides`.
     - Rebuild endpoint regenerates `core_ingredient_keys` without resetting embedding unless embedding text changed.

4. **User ingredient preference was being drowned out by vector search.**
   - Problem: if the user asked for `thịt bò`, vector/rule matches could still rank non-beef foods too high.
   - Solution used: ingredient preference is handled as a priority group:
     - If requested ingredient is not medically conflicting and any candidate matches it, those foods are ranked before non-matching alternatives.
     - If not enough matching foods exist, safe alternatives fill the remaining top 5.

5. **Medical advice sounded too confident.**
   - Problem: `ai_response` could call risky foods "phù hợp" or "an toàn" too easily.
   - Solution used: post-processing prompt now describes results as `[Top món ăn đã qua lọc và xếp hạng]`, not inherently safe; it forbids invented dish names and requires cautious language for risky but preference-matching dishes.

6. **UI needed per-card explainability.**
   - Problem: frontend food cards had "Tại sao lại gợi ý?" but backend did not return a real reason.
   - Solution used: `FoodResult.reason` is now generated by a deterministic template from matched ingredient, context, medical prefer tags, avoid tags, and score details.

7. **Roadmap/API scope was unclear.**
   - Solution used: added `docs/backend_api_todo.md` to define missing API modules, priorities, and file/folder ownership for future implementation.

### Current search architecture

Current flow:

1. `supervisor_agent` extracts health constraints, ingredients, dish names, and soft/category preferences.
2. `resolve_food_conflicts` merges user preferences with medical rules from `tags`.
3. Ingredient exclusions are converted to `core_ingredient_keys`.
4. SQL filters foods using `Food.core_ingredient_keys.overlap(...)`.
5. Context filters use `meal_context` and `occasion_context` adaptively.
6. Ingredient include preferences create a priority group.
7. Query is embedded with text aligned to food embedding fields.
8. Cosine score is adjusted with tag/category bonus/penalty.
9. Top 5 results include `reason`.
10. `post_processing_agent` injects `medical_advice_rules.json` and writes cautious advice.

## 1. High-Level Purpose

This backend is a FastAPI food recommendation system. The main user-facing flow is:

1. User asks a natural-language food query.
2. LLM extracts health constraints, liked/disliked ingredients, liked/disliked dish names, and soft tag preferences.
3. Backend applies medical and user filters.
4. Backend ranks remaining foods by embedding similarity.
5. Backend returns top foods plus a natural-language dietary explanation.

The system is not only a search engine. It also acts as a safety-aware recommendation system for users with diseases, allergies, or dietary constraints.

## 3. Database Models

Defined in `models.py`.

### `Food`

Fields used by the search flow:

- `name`: dish name.
- `description`: natural language description used in embedding text.
- `img_url`: optional image URL.
- `core_ingredients`: normalized display/search ingredients used in embedding text.
- `raw_ingredients`: original crawled ingredient lines with quantities/notes.
- `raw_instructions`: original cooking instructions.
- `core_ingredient_keys`: normalized `base:*`, `canon:*`, and `group:*` keys used for deterministic ingredient filtering.
- `soft_tags`: dish attributes such as method/form/nutrition/cuisine.
- `taste_profile`: taste category, for example `Thanh đạm`, `Đậm đà`, `Béo ngậy`.
- `meal_context`: meal timing, for example `Ăn sáng`, `Ăn trưa`, `Ăn tối`.
- `occasion_context`: usage context, for example `Ăn no`, `Ăn vặt`, `Ấm bụng`.
- `embedding`: `HALFVEC(3072)`, generated by `gemini-embedding-001`.

Important: `raw_ingredients`, `raw_instructions`, and `core_ingredient_keys` are stored for traceability/filtering. They are not directly embedded. Embedding text uses `name`, `description`, `core_ingredients`, `soft_tags`, `taste_profile`, `meal_context`, and `occasion_context`.

### `Tag`

Represents health/allergy rule definitions:

- `name`: health condition or allergy name.
- `tag_type`: for example `DISEASE` or `ALLERGY`.
- `exclude_soft_tag`: soft tags to block.
- `prefer_soft_tag`: soft tags to prefer.
- `exclude_ingredient`: ingredients to hard-block.
- `prefer_ingredient`: ingredients to prefer.

## 4. API Response Shape

Defined in `schemas.py`.

`SearchResponse` contains:

- `query`: original query.
- `ai_insight`: extracted/derived medical and preference context.
- `results`: list of `FoodResult`.
- `ai_response`: optional natural-language advice from the post-processing agent.

`FoodResult` contains:

- `id`
- `name`
- `description`
- `img_url`
- `core_ingredients`
- `soft_tags`
- `taste_profile`
- `meal_context`
- `occasion_context`
- `matchScore`
- `reason`: short per-card explanation for "Tại sao lại gợi ý?"

## 5. Search Flow in `services/food_service.py`

### Step 1: Intent Extraction

Function:

- `supervisor_agent(user_input)`

Uses Gemini JSON schema mode to extract:

- `health_constraints`
- `include_dishes`
- `exclude_dishes`
- `include_ingredients`
- `exclude_ingredients`
- `include_soft_tags`
- `exclude_soft_tags`

Allowed health tags and soft tags are hardcoded in `food_service.py`. Keep them synchronized with `standard-data/tags_data.json` and `scripts/relabel_soft_tags.py`.

### Step 2: Resolve Medical Conflicts

Function:

- `resolve_food_conflicts(user_input, db)`

Behavior:

- Canonicalizes health tag aliases.
- Loads matching `Tag` rows from DB.
- Combines user dislikes with medical `exclude_ingredient`.
- Combines user preferences with medical `prefer_soft_tag` and `prefer_ingredient`.
- For `ALLERGY`, the backend currently avoids broad `exclude_soft_tag` blocking and mainly blocks via `exclude_ingredient`.

Reason: blocking allergy by broad soft tags such as `Hải sản` can wrongly remove safe foods. Example: shellfish allergy should not automatically block all fish.

### Step 3: Enriched Query

`search_food` creates an expanded text query from:

- original user query
- requested dish names
- preferred soft tags
- preferred ingredients

This expanded query is embedded with:

- model: `gemini-embedding-001`
- output dimension: `3072`
- task type: `RETRIEVAL_QUERY`

### Step 4: Hard Filtering

Filtering happens before vector ranking:

1. Medical/user excluded ingredients are converted to ingredient keys using `services.ingredient_key_service.generate_filter_keys`.
2. SQL filters food rows with `not_(Food.core_ingredient_keys.overlap(exclude_ingredient_keys))`.
2. SQL excludes dish names the user does not want.
3. Python safety filter checks the same key overlap for data that may not have been rebuilt yet.

Important: disease/allergy safety now depends on both `core_ingredients` quality and alias/key coverage in `core_ingredient_keys`.

### Step 5: Category Context and Ingredient Priority

After hard filtering:

- User `meal_context` and `occasion_context` are applied with adaptive context filters.
- User included ingredients become a priority group if they do not conflict with medical exclusions.
- If at least one safe candidate matches the requested ingredient, matching foods are sorted ahead of non-matching alternatives.
- If not enough matching foods exist, safe alternatives fill the top 5.

Soft/category tags are no longer treated as a broad hard filter by default. They are mostly used for score bonus/penalty and explanation.

### Step 6: Vector Ranking

Cosine similarity is computed in memory between:

- query embedding
- each remaining food embedding

The base cosine score is adjusted with:

- user soft/taste/context bonus
- medical prefer tag bonus
- user/medical avoid tag penalty

Top 5 foods are returned with `FoodResult.reason`.

### Step 7: Dynamic Rule Injection Advice

Function:

- `post_processing_agent(user_query, user_symptoms, top5_foods, retrieval_notes=None)`

Uses `medical_advice_rules.json`.

This file does not block foods. It only injects dietary advice for foods that already passed hard filters and soft tag filters.

The agent:

1. Collects all soft tags and core ingredients from top 5 foods.
2. Loads general advice for each disease.
3. Adds conditional warnings when a food tag/ingredient matches the rule trigger.
4. Calls Gemini to write a short user-facing explanation.

Current prompt guardrails:

- Results are described as "Top món ăn đã qua lọc và xếp hạng", not guaranteed absolutely safe.
- The LLM is not allowed to invent dish names outside the top results.
- Risky but preference-matching foods must use cautious language, for example "có thể cân nhắc nếu điều chỉnh".

## 7. Relabel Logic

Main script:

- `scripts/relabel_soft_tags.py`

Purpose:

- Reads `raw_foods_input.json`.
- Calls Gemini dish by dish.
- Produces enriched output with:
  - `name`
  - `description`
  - `core_ingredients`
  - `preprocessing_ingredients`
  - `soft_tags`
  - `raw_ingredients`
  - `ingredients`
  - `raw_instructions`

Input distinction:

- `raw_ingredients`: display/cooking recipe data with units and quantities.
- `ingredients`: normalized search/filter data.

Do not mix these roles. `raw_ingredients` is for display; `ingredients` and `core_ingredients` are for search/filter.

### Soft Tag Philosophy

`soft_tags` should describe the main nature of the dish, not every incidental ingredient.

Examples:

- Do not tag `Ngọt` just because a savory dish has sugar.
- Do not tag `Mặn` just because a dish has salt or fish sauce.
- Do not tag `Cay` just because a dish has one chili as garnish.
- Do not tag `Giòn / Giòn rụm` for noodle dishes just because they have crispy toppings.
- Do not tag `Dai / Sần sật` for normal noodle texture unless the main ingredient is notably chewy.

Current post-processing rules handle:

- valid tag whitelist
- tag count limit, 3-8 tags
- required taste/form/method tags
- taste false positives
- method correction for obvious names/instructions
- one dish form tag only
- Vietnamese/Asian/Western category correction
- seafood/offal/protein heuristics
- allergy-relevant ingredient cleanup
- core ingredient cleanup for generic values like `nước`, `nước lọc`, `nước chan`, `gia vị`

## 8. Audit Logic

## 11. Category Migration Result

The project moved meal/taste/occasion tags out of `soft_tags`.

Current category fields:

- `taste_profile`: `Đậm đà`, `Thanh đạm`, `Chua`, `Cay`, `Mặn`, `Ngọt`, `Đắng`, `Béo ngậy`
- `meal_context`: `Ăn sáng`, `Ăn trưa`, `Ăn tối`, `Ăn chiều / xế`, `Ăn khuya`
- `occasion_context`: `Ăn no`, `Ăn vặt`, `Mồi nhậu`, `Tráng miệng`, `Giải rượu`, `Giải cảm`, `Ấm bụng`

Why:

- Keeps `soft_tags` less noisy.
- Makes future filtering/ranking more explicit.
- Avoids using meal timing or taste as medical safety signals by accident.

Implemented:

- DB fields in `Food`.
- Pydantic response fields in `FoodResult`.
- Seed logic from the clean categorized data file.
- Food embedding text includes category fields.
- Search query expansion mirrors food embedding text.
- Adaptive context filter for meal/occasion.
- Score bonus/penalty uses combined `soft_tags`, `taste_profile`, `meal_context`, and `occasion_context`.

Remaining improvement:

- Add a formal regression test runner for category behavior.
- Continue cleaning category labels as new bad cases are discovered.

## 13. Known Risks and Traps

### Data quality issues

Some dish names and ingredients may not align. Example found during audit:

- `Rau muống xào tỏi` has `ốc giác` in ingredients.

This may be a real dish variant, a bad crawl, or a wrong title. Do not blindly patch soft-tag rules to hide bad source data.

### Ingredient normalization issues

LLM may normalize ingredients in ways that do not literally appear in source:

- `carot` -> `cà rốt`
- `xà lát` -> `xà lách`
- `cốt bánh` -> `cốt bánh bông lan`

Some of these are acceptable normalization. Others may be hallucination. Audit reports mark them as `core_not_grounded`.

### Vietnamese substring traps

Use phrase matching, not loose substring matching.

Known false positives:

- `cá` inside `các`
- `lòng` inside `lòng đỏ trứng`
- `bơ` in dish names causing accidental dairy tagging

### Form-tag traps

Do not classify all `miến` as `Món nước`.

Examples:

- `Miến trộn` should be `Món khô`.
- `Miến xào` should be `Món khô`.
- `Miến nước` can be `Món nước`.

### Origin/category traps

Do not classify all dishes with Vietnamese words as `Món Việt truyền thống`.

Examples:

- `Omurice` should be `Món Á`.
- `Udon` should be `Món Á`.
- `Indomie` should be `Món Á` or `Thức ăn nhanh`.
- `Pizza` should be `Món Âu` / `Thức ăn nhanh`.

### Allergy safety

Never rely only on broad soft tags for allergies.

Example:

- Shellfish allergy should be handled by ingredients like `tôm`, `cua`, `ghẹ`, not only by `Hải sản`.

### Medical correctness

Rules are heuristic and project-specific. They are not guaranteed medical advice. UI/API should include a disclaimer that recommendations are for reference and users with medical conditions should consult professionals.
