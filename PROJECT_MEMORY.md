# PROJECT MEMORY - Food Recommendation Backend

Last updated: 2026-05-13

This file is a working memory for future AI agents or engineers. It summarizes how the backend works, what data files mean, what is currently reliable, and what is still in progress.

## 1. High-Level Purpose

This backend is a FastAPI food recommendation system. The main user-facing flow is:

1. User asks a natural-language food query.
2. LLM extracts health constraints, liked/disliked ingredients, liked/disliked dish names, and soft tag preferences.
3. Backend applies medical and user filters.
4. Backend ranks remaining foods by embedding similarity.
5. Backend returns top foods plus a natural-language dietary explanation.

The system is not only a search engine. It also acts as a safety-aware recommendation system for users with diseases, allergies, or dietary constraints.

## 2. Runtime Entry Points

Main API entrypoint:

- `main.py`
- FastAPI app title: `Food AI API`
- Endpoint: `GET /foods/search?q=...`
- Handler: `services.food_service.search_food`

Startup behavior:

1. Creates database tables with SQLAlchemy.
2. Ensures PostgreSQL `vector` extension exists.
3. Runs `services.seed_service.seed_data()`.
4. Seeds medical tags from `standard-data/tags_data.json`.
5. Seeds foods from `foods_enriched.json`.
6. Creates Gemini embeddings for foods whose `embedding` is `NULL`.

Local run command:

```bash
source venv/bin/activate
python -m uvicorn main:app --reload
```

If port is busy, use another port:

```bash
python -m uvicorn main:app --reload --port 8001
```

## 3. Database Models

Defined in `models.py`.

### `Food`

Fields used by the search flow:

- `name`: dish name.
- `description`: natural language description used in embedding text.
- `img_url`: optional image URL.
- `core_ingredients`: normalized ingredients used for filtering and embedding.
- `soft_tags`: dish attributes used for filtering, ranking context, and medical warnings.
- `embedding`: `HALFVEC(3072)`, generated by `gemini-embedding-001`.

Important: current DB model does not store `raw_ingredients`, `raw_instructions`, or category fields.

### `Tag`

Represents health/allergy rule definitions:

- `name`: health condition or allergy name.
- `tag_type`: for example `DISEASE` or `ALLERGY`.
- `exclude_soft_tag`: soft tags to block.
- `prefer_soft_tag`: soft tags to prefer.
- `exclude_ingredient`: ingredients to hard-block.
- `prefer_ingredient`: ingredients to prefer.

## 4. API Response Shape

Defined in `schemas.py`.

`SearchResponse` contains:

- `query`: original query.
- `ai_insight`: extracted/derived medical and preference context.
- `results`: list of `FoodResult`.
- `ai_response`: optional natural-language advice from the post-processing agent.

`FoodResult` contains:

- `id`
- `name`
- `description`
- `img_url`
- `core_ingredients`
- `soft_tags`
- `matchScore`

## 5. Search Flow in `services/food_service.py`

### Step 1: Intent Extraction

Function:

- `supervisor_agent(user_input)`

Uses Gemini JSON schema mode to extract:

- `health_constraints`
- `include_dishes`
- `exclude_dishes`
- `include_ingredients`
- `exclude_ingredients`
- `include_soft_tags`
- `exclude_soft_tags`

Allowed health tags and soft tags are hardcoded in `food_service.py`. Keep them synchronized with `standard-data/tags_data.json` and `scripts/relabel_soft_tags.py`.

### Step 2: Resolve Medical Conflicts

Function:

- `resolve_food_conflicts(user_input, db)`

Behavior:

- Canonicalizes health tag aliases.
- Loads matching `Tag` rows from DB.
- Combines user dislikes with medical `exclude_ingredient`.
- Combines user preferences with medical `prefer_soft_tag` and `prefer_ingredient`.
- For `ALLERGY`, the backend currently avoids broad `exclude_soft_tag` blocking and mainly blocks via `exclude_ingredient`.

Reason: blocking allergy by broad soft tags such as `Hải sản` can wrongly remove safe foods. Example: shellfish allergy should not automatically block all fish.

### Step 3: Enriched Query

`search_food` creates an expanded text query from:

- original user query
- requested dish names
- preferred soft tags
- preferred ingredients

This expanded query is embedded with:

- model: `gemini-embedding-001`
- output dimension: `3072`
- task type: `RETRIEVAL_QUERY`

### Step 4: Hard Filtering

Filtering happens before vector ranking:

1. SQL filters food rows by excluded ingredients using `ILIKE` over `array_to_string(Food.core_ingredients, ',')`.
2. SQL excludes dish names the user does not want.
3. Python filter `_food_has_excluded_ingredient` runs accent-insensitive phrase matching to catch extra ingredient matches.

Important: disease/allergy safety depends heavily on the quality of `core_ingredients`.

### Step 5: Soft Tag Blocking

After initial filtering, the code builds `banned_tags` from:

- medical excluded tags
- user excluded soft tags

Each food's `soft_tags` are canonicalized. If a banned tag intersects with the food tags, that food is removed before similarity scoring.

### Step 6: Vector Ranking

Cosine similarity is computed in memory between:

- query embedding
- each remaining food embedding

Top 5 foods are returned.

### Step 7: Dynamic Rule Injection Advice

Function:

- `post_processing_agent(user_query, user_symptoms, top5_foods)`

Uses `medical_advice_rules.json`.

This file does not block foods. It only injects dietary advice for foods that already passed hard filters and soft tag filters.

The agent:

1. Collects all soft tags and core ingredients from top 5 foods.
2. Loads general advice for each disease.
3. Adds conditional warnings when a food tag/ingredient matches the rule trigger.
4. Calls Gemini to write a short user-facing explanation.

## 7. Relabel Logic

Main script:

- `scripts/relabel_soft_tags.py`

Purpose:

- Reads `raw_foods_input.json`.
- Calls Gemini dish by dish.
- Produces enriched output with:
  - `name`
  - `description`
  - `core_ingredients`
  - `preprocessing_ingredients`
  - `soft_tags`
  - `raw_ingredients`
  - `ingredients`
  - `raw_instructions`

Input distinction:

- `raw_ingredients`: display/cooking recipe data with units and quantities.
- `ingredients`: normalized search/filter data.

Do not mix these roles. `raw_ingredients` is for display; `ingredients` and `core_ingredients` are for search/filter.

### Soft Tag Philosophy

`soft_tags` should describe the main nature of the dish, not every incidental ingredient.

Examples:

- Do not tag `Ngọt` just because a savory dish has sugar.
- Do not tag `Mặn` just because a dish has salt or fish sauce.
- Do not tag `Cay` just because a dish has one chili as garnish.
- Do not tag `Giòn / Giòn rụm` for noodle dishes just because they have crispy toppings.
- Do not tag `Dai / Sần sật` for normal noodle texture unless the main ingredient is notably chewy.

Current post-processing rules handle:

- valid tag whitelist
- tag count limit, 3-8 tags
- required taste/form/method tags
- taste false positives
- method correction for obvious names/instructions
- one dish form tag only
- Vietnamese/Asian/Western category correction
- seafood/offal/protein heuristics
- allergy-relevant ingredient cleanup
- core ingredient cleanup for generic values like `nước`, `nước lọc`, `nước chan`, `gia vị`

## 8. Audit Logic

Main script:

- `scripts/audit_soft_tag_output.py`

Purpose:

- Reads relabel output.
- Finds likely tagging problems.
- Writes a markdown report.

Severity levels:

- `P0`: structural failure; do not run full relabel as production.
- `P1`: likely wrong label; patch logic before full production use.
- `P2`: review manually; often data quality or grounding issue.

Common audit codes:

- `invalid_tag`
- `bad_tag_count`
- `bad_form_count`
- `missing_method`
- `missing_taste`
- `suspicious_form`
- `method_name_mismatch`
- `sweet_false_positive`
- `salty_false_positive`
- `sour_false_positive`
- `spicy_false_positive`
- `rich_false_positive`
- `texture_topping_crunchy`
- `texture_noodle_chewy`
- `missing_seafood`
- `seafood_false_positive`
- `hidden_seafood_in_ingredients`
- `vegetarian_conflict`
- `missing_offal`
- `offal_false_positive`
- `missing_protein`
- `protein_false_positive`
- `healthy_conflict`
- `dessert_false_positive`
- `core_not_grounded`

Example audit commands:

```bash
venv/bin/python scripts/relabel_soft_tags.py \
  --sample 120 \
```

## 9. Medical Rule Logic

### Hard Filter Rules

Source:

- `standard-data/tags_data.json`

Used by:

- `services/seed_service.py`
- DB table `tags`
- `services.food_service.resolve_food_conflicts`

Fields:

- `exclude_ingredient`: hard-block ingredients.
- `exclude_soft_tag`: broad soft-tag block for disease rules.
- `prefer_ingredient`: boosts query context.
- `prefer_soft_tag`: boosts query context.

Important behavior:

- For `tag_type == "ALLERGY"`, broad `exclude_soft_tag` is not used for blocking in `resolve_food_conflicts`.
- Allergy safety relies on `exclude_ingredient` and accurate `core_ingredients`.

### Dynamic Advice Rules

Source:

- `medical_advice_rules.json`

Used by:

- `post_processing_agent`

Purpose:

- Give eating advice/warnings after hard filters.
- It does not block dishes.

Current state:

- Contains rules for all 32 health/allergy tags currently present in `standard-data/tags_data.json`.

## 11. Category Migration Idea

The project previously identified that some tags should eventually move out of `soft_tags`.

Suggested future category fields:

- `taste_profile`: `Đậm đà`, `Thanh đạm`, `Chua`, `Cay`, `Mặn`, `Ngọt`, `Đắng`, `Béo ngậy`
- `meal_context`: `Ăn sáng`, `Ăn trưa`, `Ăn tối`, `Ăn chiều / xế`, `Ăn khuya`
- `occasion_context`: `Ăn no`, `Ăn vặt`, `Mồi nhậu`, `Tráng miệng`, `Giải rượu`, `Giải cảm`, `Ấm bụng`

Why:

- Keeps `soft_tags` less noisy.
- Makes future filtering/ranking more explicit.
- Avoids using meal timing or taste as medical safety signals by accident.

Not yet implemented:

- DB fields
- Pydantic response fields
- seed logic
- search ranking changes
- relabel output schema

Proposed high-level graph from the current design:

1. `Start`
2. `Load_User_Profile`
3. `Router/Supervisor`
4. `SQL Agent`
5. `RAG Agent`
6. `Map Agent`
7. `Final Response`
8. `Update_User_Profile`
9. `End`

Supporting/background agents:

- `Crawler Agent`
- `Enricher Agent`
- `Indexing Agent`

1. `agentic-rag`
2. `hybrid-retrieval`
3. `corrective-rag`
4. `rag-evaluation`

6. `graphrag-patterns`

Skill-to-agent mapping:

| Skill file | Useful for | Priority |
|---|---|---|
| `.agents/skills/agentic-rag/SKILL.md` | LangGraph state design, `Router/Supervisor`, `RAG Agent`, query decomposition, tool-using agent flow | Very high |
| `.agents/skills/hybrid-retrieval/SKILL.md` | `SQL Agent`, `RAG Agent`, combining structured filters, keyword search, and vector search | Very high |
| `.agents/skills/corrective-rag/SKILL.md` | Result validation, safety grading, fallback routing, self-correction when retrieval is weak or unsafe | High |
| `.agents/skills/rag-evaluation/SKILL.md` | Evaluation set, retrieval metrics, disease-query tests, regression tests | High |
| `.agents/skills/production-rag-checklist/SKILL.md` | Production readiness, indexing pipeline, monitoring, cache, rate limiting, reliability | Medium-high |
| `.agents/skills/graphrag-patterns/SKILL.md` | Future knowledge graph over foods, ingredients, diseases, soft tags, and medical rules | Medium, later phase |

Suggested implementation phases:

1. Stabilize the current food recommendation flow first: full relabel, audit, category migration, disease-search tests.
2. Extract current `search_food` logic into tool-like units: intent extraction, hard filter, vector retrieval, safety validation, final explanation.
3. Build LangGraph `State` with user query, user profile, extracted constraints, candidate foods, rejected foods, warnings, final answer, and profile updates.
4. Implement `Router/Supervisor` to decide whether the query needs SQL filtering, RAG search, crawler/enrichment, or direct response.
5. Implement `SQL Agent` for deterministic filtering by health rules, allergies, ingredients, categories, and user profile.
6. Implement `RAG Agent` for semantic/hybrid retrieval over food descriptions, ingredients, tags, and future documents.
7. Implement `Map Agent` to transform candidate foods into final ranked recommendations with reasons and warnings.
8. Add `Corrective/Safety Grader` before final response to catch unsafe or weak recommendations.
9. Add evaluation with fixed test queries before using the agentic flow in production.
10. Add `Crawler`, `Enricher`, and `Indexing` as background/offline agents, not in the critical user request path at first.

Important design note:

Do not build the LangGraph layer until the current dataset and medical filtering behavior are stable enough. Agentic orchestration will amplify data-quality problems if relabeling, categories, or medical rules are still noisy.

## 13. Known Risks and Traps

### Data quality issues

Some dish names and ingredients may not align. Example found during audit:

- `Rau muống xào tỏi` has `ốc giác` in ingredients.

This may be a real dish variant, a bad crawl, or a wrong title. Do not blindly patch soft-tag rules to hide bad source data.

### Ingredient normalization issues

LLM may normalize ingredients in ways that do not literally appear in source:

- `carot` -> `cà rốt`
- `xà lát` -> `xà lách`
- `cốt bánh` -> `cốt bánh bông lan`

Some of these are acceptable normalization. Others may be hallucination. Audit reports mark them as `core_not_grounded`.

### Vietnamese substring traps

Use phrase matching, not loose substring matching.

Known false positives:

- `cá` inside `các`
- `lòng` inside `lòng đỏ trứng`
- `bơ` in dish names causing accidental dairy tagging

### Form-tag traps

Do not classify all `miến` as `Món nước`.

Examples:

- `Miến trộn` should be `Món khô`.
- `Miến xào` should be `Món khô`.
- `Miến nước` can be `Món nước`.

### Origin/category traps

Do not classify all dishes with Vietnamese words as `Món Việt truyền thống`.

Examples:

- `Omurice` should be `Món Á`.
- `Udon` should be `Món Á`.
- `Indomie` should be `Món Á` or `Thức ăn nhanh`.
- `Pizza` should be `Món Âu` / `Thức ăn nhanh`.

### Allergy safety

Never rely only on broad soft tags for allergies.

Example:

- Shellfish allergy should be handled by ingredients like `tôm`, `cua`, `ghẹ`, not only by `Hải sản`.

### Medical correctness

Rules are heuristic and project-specific. They are not guaranteed medical advice. UI/API should include a disclaimer that recommendations are for reference and users with medical conditions should consult professionals.
